# Realtime Recovery Events (SSE)

**GitHub Issue:** [#46](https://github.com/Genghis-codes/Stellar-Global-Wallet/issues/46)

## Summary

The backend indexes Soroban contract events and pushes them to connected clients over Server-Sent Events (SSE). Owners learn when a recovery has started; guardians learn when their approval is needed.

## Motivation

A recovery that starts silently is a security incident. An owner who doesn't know a recovery is in progress cannot revoke it in time. A guardian who doesn't know they're needed makes recovery impossible. Push events close that gap without polling.

## Endpoint

```
GET /api/v1/stream/recovery
```

### Authentication

Requires a valid JWT in the `Authorization: Bearer <token>` header.  
The connection is filtered server-side to events relevant to the authenticated identity (owner or guardian).

### Query Parameters

| Parameter      | Type   | Required | Description                                      |
|----------------|--------|----------|--------------------------------------------------|
| `lastEventId`  | string | No       | Resume from this event ID (sent as `Last-Event-ID` header by the SDK) |

### SSE Event Format

Each event follows the standard SSE format and matches the `EventEnvelope` schema defined in [realtime-event-schema.md](./realtime-event-schema.md):

```
id: <uuid>
event: recovery.initiated
data: {"type":"recovery.initiated","id":"…","occurredAt":"2026-10-18T12:00:00Z","version":1,"data":{"contractId":"…","proposer":"G…","newOwner":"G…","expiresAt":"…"}}

```

### Emitted Event Types

| SSE `event` field       | Trigger                                                  | Recipients        |
|-------------------------|----------------------------------------------------------|-------------------|
| `recovery.initiated`    | A recovery proposal is created on-chain                  | Owner + guardians |
| `recovery.approved`     | A guardian signs approval                                | Owner + guardians |
| `recovery.revoked`      | A guardian revokes their prior approval                  | Owner + guardians |
| `recovery.executed`     | Approval threshold reached; ownership transferred        | Owner + guardians |
| `recovery.cancelled`    | Recovery cancelled before execution threshold            | Owner + guardians |

A `heartbeat` comment (`: ping`) is sent every 15 seconds to prevent proxy timeouts.

## Architecture

```
Soroban contract events
        │
        ▼
  Indexer (poll / getEvents RPC)
        │  publishes to
        ▼
  In-process event bus  (or Redis pub/sub for multi-instance deployments)
        │  fan-out to
        ▼
  SSE connections   ──filter by account/guardian──►  client
```

- The indexer polls `soroban_rpc.getEvents` on each new ledger and publishes matching events to the bus.
- The SSE handler subscribes to the bus and writes events to all matching open connections.
- Filtering happens at write time: an event is only written to a connection whose authenticated identity matches the event's `contractId` owner or guardian list.

## Connection Lifecycle

| Phase | Behaviour |
|---|---|
| Connect | JWT validated; connection added to the fan-out map |
| Heartbeat | `: ping` comment sent every 15 s |
| Reconnect | Client sends `Last-Event-ID`; server replays buffered events since that ID (buffer TTL: 5 min) |
| Disconnect | Connection removed from fan-out map; buffered events retained for TTL |
| Per-connection limits | Max 512 queued messages; connection closed if limit exceeded |

## Memory and Rate Limits

- Each open connection holds at most **512 pending messages** in its write buffer.
- A single account may hold at most **10 concurrent SSE connections**. The oldest is closed when the limit is exceeded.
- The event replay buffer is capped at **1 000 events per account** with a **5-minute TTL**.

## Implementation Notes

- For single-instance deployments the event bus is in-process (an `EventEmitter` or equivalent).
- For multi-instance deployments swap the bus for Redis pub/sub without changing the SSE handler.
- All event IDs are stable UUIDs generated by the indexer, enabling idempotent client-side deduplication.
- Authorization (`require_auth`) is enforced at the connection level; the indexer does not filter before publishing.
